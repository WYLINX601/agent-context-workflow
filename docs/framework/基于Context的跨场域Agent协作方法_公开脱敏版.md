在实际工作中，**理解项目、形成方案、验证判断、推动协作和沉淀经验，往往发生在不同工具和协作空间**中。AI 参与企业协作，真正的问题是人与不同 Agent 能否围绕同一件事继续工作，知道哪些信息可以相信、哪些能力可以使用，以及结果应该沉淀到哪里。

基于这个问题，一套 AI Native 工作流可以概括为：**一个 Context 底座、两种 Agent 协作方式（个人助手+Agent 小队），以及一个能力进化闭环。**

## 1、跨场域使用 Agent 的痛点：

- **重复交代**：个人同一偏好／口径，换个 Agent 或对话就要重说一遍。
- **跨场域断裂**：Agent、交互形式多种多样，底层数据不互通，Codex、Claude Code、Multica 等众多 Agent 各干各的，同一件事换工具／对话就断线。
- **结论难复用**：讨论结论散在对话线程里，沉淀不成团队能力；个人经验要在每个 Agent 上重复调教。

## 2、解决方案：Context 底座 + Agent 跨工具协作

- **Context 底座传递、沉淀任务信息**：

- 借助工作区本地 `AGENTS.md` 的指令加载能力设计上下文读取规则，让 Agent 按需读取个人 Context（如何协作、使用哪些方法）+ 项目／需求 Context（这件事是什么、做到哪）。
- **按需加载 + 可续办**：任何地点、任何 Agent 都能按需加载任务上下文，继续未完成的工作。
- **确认写回**：结论先入候选、确认后落盘；可复用方法进能力候选反哺。

- **自由探索协作方式**：结合各 Agent 特点选最优交互形式（Codex 助手、Multica 产品方案小队、组织群聊），实现任务内容互通。

### 2.2 两类产出：项目上下文 + 团队经验

- **项目知识**：一份可复用的项目 Context，后续可持续承接相关任务。
- **团队经验**：一套评估框架（产品方案）+ 一轮迭代的 Skill + 一份需求工作 Workflow（人机协作方案）。

## 3、个人 Context 能力基建：从个人工作进入项目群

可以通过“项目／需求 Context”+“个人运行时 Memory”两层结构，建立可协作、可复用的 Context 结构。

1. 当工作进入**项目群**，协作中心会从**“个人 Context”**切换为**“项目的公共事实”**。

2. **每个人搭建一个 Context 系统（项目／需求）**，通过企业 AI 形成的方案、结论、待办和验证结果，沉淀在 Context 里面；
3. **项目 Context 可共享**，不同场域的协作办公 AI 可以快速唤起 Context；
4. 进入不同办公场域的是用户分享、共创的项目公共内容，而不是成员的完整个人 Context。

**以群为例：**

1. **工作核心围绕项目 Context**。
2. **群内 AI 助手**承担项目**协作 Leader**的角色，围绕项目 Context 调度专业 Agent。
3. **群成员可以继续补充，形成项目公共产出。**
4. 需要**深入讨论**时，同一个专业 Agent 也可以携带当前任务上下文被单独唤起，一键围绕项目／需求进行深度讨论；
5. 只有经确认的结论、成果才进入项目 Context；
6. 具有**复用价值的方法进入能力候选**，继续反哺后续 Agent。

不同入口改变的是交互方式，不变的是**工作对象——Context 来源**。

## 4、核心架构拆解

**架构的中心仍然是人**：人负责提出任务、判断方向、选择协作方式和评审结果，AI 在明确范围内承接、执行和协作。

1. **底层是一套共同的 Context。**

- **个人 Context**记录个人的协作偏好、工作方法和项目入口；
- **项目与需求 Context**记录目标、决策、任务、产物和验证状态。

3. **Agent 角色分工**

- **助手 Agent（Codex、Claude Code 等）**：范围清晰或需要持续讨论的工作进入个人共创工作台；
- **Multica 产品方案小队**：需要多专业角色分工的复杂任务进入小队协作；
- **能力交汇于 Context**：两条路径最终都回到真实工作产物，经人确认后，项目结论进入项目 Context，可复用的方法进入能力候选。

### 3.1 Context 信息结构

**任务 Context = 当前任务 + 个人 Context 切片 + 项目／需求 Context 切片 + Agent 能力配置**

- **当前任务**：定义目标、范围、交付和验收；
- **个人 Context**：提供相关偏好、方法、工作范围和约束；
- 个人 Context 内部由 `00` 找入口、`02` 定位项目和需求、`03` 提供有来源的事实、`04` 承接写回候选。
- **项目与需求 Context**：提供共同事实、决策、任务和产物；
- **Agent 能力配置**：包括专家人设、Instructions、Skills、Tools、MCP、Runtime、Model 和权限。

**Context 结构示例：**

```text
协作知识结构化沉淀/
├── AGENTS.md                         # 项目协作规则、权威顺序与写入边界
├── 输出/                              # 跨需求的汇总交付；避免作为需求事实来源
├── 需求/
│   ├── README.md                      # 需求导航与人读总览（派生视图）
│   ├── 01-协作知识沉淀示例/
│   │   ├── README.md                  # 该需求入口与产物导航
│   │   ├── 项目需求与方案文档等        # 用户可读的核心业务产物
│   │   ├── 草稿/                      # 备选方案、未定稿材料
│   │   ├── 输出/                      # 本需求生成的交付物
│   │   └── context/
│   │       ├── REQUIREMENT_CONTEXT    # 需求目标、边界、当前状态的最小摘要
│   │       ├── artifacts              # 该需求的关键产物索引
│   │       ├── tasks                  # 待办、推进状态
│   │       ├── decision-ledger        # 已确认决策与取舍
│   │       └── writeback              # 等待评审／提升的长期信息候选
│   ├── 02-知识能力接入示例/
│   ├── 03-自定义知识处理示例/
│   └── 04-知识回流示例/
└── context/
    ├── PROJECT_CONTEXT                # 项目定位、跨需求共识与全局边界
    ├── 需求全景                        # 各需求关系与整体地图
    ├── architecture                    # 总体架构或能力分层
    ├── constraints                     # 不可突破的约束、非目标
    ├── principles                      # 稳定设计原则
    ├── glossary                        # 术语表
    ├── external-dependencies           # 外部系统、依赖及验证状态
    ├── exception-ledger                # 未解决的文件、链接、归属等例外
    ├── structure-migration              # 历史结构迁移记录
    └── writeback-inbox                 # 跨需求 Context 的待评审写回候选
```

### 3.2 Agent 协作架构：个人助手与 Agent 小队

有了统一的 Context 底座后，任务可以在任何地方被唤起。

- **Codex 是个人直接共创的工作台**：适合范围相对明确，或者需要边讨论、边判断、边修改的任务。它先定位项目和需求，加载最小必要 Context，再调用 Skill 和工具操作真实产物；任务中形成的新方法先进入候选，不直接成为长期事实。
- **Multica 产品方案小队负责复杂任务的小队交付**。任务以 **Issue 记录**，**Lead Agent**明确交付目标，再拆分给产品方案、技术架构、交互设计、验证／评审等**专业 Agent**。每个 Agent 只获得与职责相关的任务 Context，Lead 负责汇总并把结果带回原 Issue。
- **产品方案小队成员**：能领取任务、留下评论、推进状态的 AI 队友。
- **进一步讨论**：人可以快速唤起对应专家，并通过“@”带入当前 Issue 上下文；讨论结论重新回到原任务链。
- **回流机制**：个人共创中形成的 Skills、经验或规则候选，经过验证、裁剪和授权后进入 Agent 能力库，再按角色配置给专业 Agent。

> 公开参考实现：本方案中的 Multica 产品方案小队采用 Go ACP Adapter 作为公开桥接资源。Adapter 只承担 ACP 与本地 Hermes Gateway 的协议适配，不包含个人 Profile、Memory、Session 或凭据。

## 让个人方法逐步转化为团队能力

这套工作流遵循四个原则：最小加载、事实有源、权限有界、写回有门。短期先让同一件工作被正确定位、正确组装，并在个人共创、小队交付和项目群协作之间保持连续。

**最终目标不是增加更多 Agent，而是建立一套持续承接真实工作的协作系统**：

- Context 提供共同坐标，个人助手支撑直接共创，产品方案小队支撑小队交付，群聊承接公共协作，能力进化机制再把个人方法转化为团队可以复用的能力。
